## Smoke Tests

`core/test_smoke.py` contains three `TestCase` tests. They verify that the home, monitoring, experiments, tuning and deployment pages, plus experiment detail, run detail and tuning job detail pages, return the expected responses for logged-out and staff users. They also check staff-only controls and POST permissions. Fixtures are created in Django's test database; LLM, Terraform generation, and promotion actions are mocked.

`core/test_benchmark_command.py` contains two isolated tests for the benchmark management command's current-code report format and failure propagation. The subprocess is mocked in these tests; `python manage.py benchmark` itself was run separately to produce the measurements below.

## End-to-End Integration Tests

`experiments/test_lifecycle.py` contains three integration tests using real test-database rows:

- Run registration through the training command, including experiment/run versions, parent relationship, recorded parameters and metrics, change data, data hash and comparison-page output. Model fitting is mocked.
- Prediction message handling through persisted prediction rows and computed metric snapshots to monitoring dashboard output. RabbitMQ and LLM services are not contacted.
- Staff deployment-generation POST through session persistence and result rendering. The generator and Terraform availability check are mocked; no deployment is performed.

## Performance Benchmark

Run the benchmark with:

```bash
python manage.py benchmark
```

This command wraps the existing `core.test_performance` Django test in a test-runner subprocess. It uses fixed database fixtures, two warm-up requests, and 40 measured requests per representative route. It reports median and nearest-rank p95 latency and captures query counts. The Day 4 profiler additionally times template rendering and SQL execution. Add `--output PATH` to save a plain-text measurement report.

The files `docs/benchmarks/before.txt` and `docs/benchmarks/after.txt` were generated by running the command twice with `--output`. Both are measurements of the same current code at their recorded timestamps, not historical pre-optimization and post-optimization baselines. No genuine earlier benchmark artifact exists in this repository, and no production optimization was made.

The benchmark uses Python 3.12.3, Django 4.2.30 and an in-memory SQLite test database on Linux x86_64. It is an in-process, authenticated test client with no concurrency, not production load testing. LLM, RabbitMQ, Terraform, socket and model-training work is mocked or guarded. Deployment POST timing excludes generation and any real deployment.

The original uninstrumented monitoring-dashboard sample was **7.337 ms median / 13.511 ms p95**, with **4 SQL queries**. Repeated Day 4 instrumented runs measured:

| Run | Median (ms) | p95 (ms) | Template median (ms) | SQL execution median (ms) | Queries |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 | 7.402 | 10.399 | 4.505 | 0.149 | 4 |
| 2 | 6.616 | 11.352 | 4.222 | 0.134 | 4 |
| 3 | 5.568 | 12.167 | 3.389 | 0.125 | 4 |
| 4 | 6.028 | 9.881 | 3.542 | 0.143 | 4 |
| 5 | 5.923 | 11.470 | 3.601 | 0.128 | 4 |

On the final rerun, the dashboard measured **5.990 ms median / 10.810 ms p95** in the normal full-suite run and **10.670 ms / 16.978 ms** under coverage instrumentation; both retained four queries. The coverage-instrumented measurement is not directly comparable to the normal run. The variation between repeated runs means these samples do not establish a reliable timing improvement or regression.

## Optimization Findings

The four dashboard queries serve separate displayed data: model choices, prediction aggregates, ordered metric snapshots for charts/anomaly counts, and the latest 20 predictions. No duplicate query or N+1 pattern was demonstrated. SQLite SQL execution was roughly 0.13 ms median across the repeated instrumented profiles, while template rendering was roughly 3.4-4.5 ms. These small-fixture measurements identify no meaningful optimization that can be justified while preserving current output, so production dashboard code was left unchanged. No before/after optimization claim is made.

## Limitations

- The test database is SQLite and the fixtures are small; query plans and timings may differ substantially with production data or another database engine.
- Test-client timings exclude network, browser, reverse-proxy and concurrent-user effects.
- Coverage instrumentation adds measurable request overhead; do not compare covered and uncovered latency as if they were equivalent runs.
- External services and expensive training/deployment operations are intentionally not exercised. These tests verify application behavior around mocked integration boundaries, not external-service performance or successful cloud deployment.
- No performance service-level target is documented, so the benchmark has no arbitrary latency pass/fail threshold.
